## AI Agents overview

The **AI Agents** page is the main workspace for creating and managing agents in Callin. From here, you can see your agents in one place, identify which ones are inbound or outbound, open any setup to edit it, and create new ones for different business flows.

This page is especially useful when you want to create a new agent for calls or website conversations, separate agents by purpose, quickly find an existing setup, and detect unfinished configurations before going live.

In the list view, you can usually review the agent name, call direction, language tag, creation date, and action icons. You may also see warnings such as a missing phone number, which helps you catch incomplete setups before using the agent in production.

To create a new agent, open the AI Agents page, click **Create Agent**, choose whether to start from scratch or use a template, enter the agent name, and then confirm the creation.

This page includes:

- **Agent**
- **Workflow**
- **Knowledge Base**
- **Tools**
- **Call Action**
- **Website widget**
- **Advanced**

> **Tip:** A clean AI Agents setup is easier to test, easier to maintain, and much safer to move into production.

The **Agent** tab defines the main configuration of your assistant. This is where you set how it should behave during a call, how it should open the conversation, which voice it will use, which languages it can handle, which AI model will generate responses, and whether it will work with inbound calls, outbound calls, or both.

A strong setup in this tab creates clearer, more natural, and more consistent interactions. A generic setup usually leads to weaker openings, less precise responses, and a less controlled customer experience.

### Conversation Prompt

**Conversation Prompt** is the main instruction set for the agent. This is where you define the conversation logic, identity, working context, tone, and operational limits.

This block determines how the agent interprets the call and how it should respond. It is the internal foundation that guides model behavior during the conversation.

The recommended structure is the one already organized inside the prompt itself. The base sections are **Personality**, **Environment**, and **Tone**. From there, the prompt should continue with operational rules and clear restrictions.

- Define who the agent is and what role it plays.
- Describe the environment in which it operates.
- Set the tone the agent should maintain.
- Explain what the agent should prioritize in each response.
- State what the agent must avoid.
- Clarify how the agent should use the knowledge base.
- Define how the conversation should move forward.

### How to write the prompt well

A good prompt gives the agent a clear role, a clear context, and a clear decision logic. It should sound operational, not decorative.

For support agents, a practical structure is to define the assistant as a level-one support agent, explain that it helps platform users, and instruct it to rely on the knowledge base while answering in a calm, concise, step-by-step way.

- Ask only one clarifying question at a time.
- Always move the user toward the next useful step.
- Use the knowledge base for reference answers.
- Extract only the information needed for the current step.
- Keep answers brief unless the user asks for more detail.

### What the agent should avoid

The prompt should also limit behaviors that damage the experience.

- Long monologues.
- Multiple questions in a single turn.
- Unnecessary repetition.
- Inventing answers when information is unclear.
- Forcing a troubleshooting path when the case should be escalated.

### Dynamic Variables in the prompt

**Conversation Prompt** supports dynamic variables inside the text. These variables let you reuse the same logic with different values without rewriting the entire prompt.

The **Add Variables** menu includes system variables, custom variables, and the option to create a new variable. When you create a new variable, it is inserted directly into the prompt and becomes available in **Dynamic Variables**, where you assign its value.

This is useful for values such as the agent name, company name, city, service name, professional name, or location name.

### Time zone and Default personality

**Conversation Prompt** includes a time zone selector. This setting defines the time context the agent will use when it needs to interpret hours, dates, availability, or references such as today, tomorrow, or this afternoon.

Always choose the real time zone of the business or service represented by the agent.

The same area also includes the **Default personality** control. This setting belongs to the base personality behavior and should be reviewed together with the prompt so the final experience matches the behavior you want to deliver.

### Greeting Message

**Greeting Message** defines the first words spoken by the agent when the conversation starts. It introduces the assistant and immediately tells the caller what kind of help is available.

A strong greeting identifies the assistant, explains the purpose of the interaction, and invites the user to continue.

- **Support example:** Hello, I am the support assistant. Tell me what you need and I will help you step by step.
- **Appointments example:** Hello, I am the appointment assistant. I can help you book, change, or cancel an appointment.
- **Reception example:** Hello, thank you for calling. I am the virtual assistant and I will help you with your request.

### Allow Interruptions

**Allow Interruptions** lets the user interrupt the agent while it is speaking. When enabled, the interaction feels more fluid and natural.

This is usually a strong default for support, reception, and general customer service. If your opening message contains a critical instruction that must be heard in full, validate this setting carefully before going live.

### Dynamic Variables

**Dynamic Variables** gathers the variables that have been inserted and the value assigned to each one. This is where you manage the practical side of each variable: name and value.

This section is especially useful when you work with multiple clients, brands, locations, or services and want to keep the same agent structure while changing only the data that varies.

### Voice

**Voice** defines the voice the agent will use during the call. Voice does not change the logic of the assistant, but it strongly shapes how the call is perceived in terms of clarity, trust, naturalness, and overall tone.

This section includes a primary voice, the option to add additional voices, voice-specific controls, and common output and latency settings.

- **Expressive Mode** controls whether the voice should sound more expressive.
- **Speed** controls how fast the voice speaks.
- **Stability** controls the balance between expressiveness and consistency.
- **Similarity** helps the voice maintain a more consistent vocal identity.

### Select Voice and additional voices

Voice selection is managed from **Select Voice**. This panel includes **Explore**, **Cloned**, and **Add**.

**Explore** contains the available voice catalog, with search, language filter, gender filter, and a short description for each voice.

**Cloned** contains the cloned or imported voices available in your environment.

**Add** lets you import a voice from ElevenLabs using a shared link and assign it a name before adding it to the agent.

**Add additional voice** is useful when one agent needs secondary voices for more languages or different customer segments.

### Common voice settings

**Common voice settings** includes two global configurations: **TTS output format** and **Optimize streaming latency**.

**TTS output format** defines the output format of the generated audio. **PCM 16000 Hz** appears as the recommended option.

**Optimize streaming latency** controls the balance between response speed and audio quality. A more optimized latency makes the agent start speaking sooner, but it may affect audio quality.

### Language

**Language** defines the primary language of the agent and the additional languages it can handle during the conversation.

The default language is the one used when the interaction begins. Additional languages let the same agent support multilingual conversations.

Enable only the languages you actually need. A cleaner configuration usually produces more stable behavior.

### AI Intelligence

**AI Intelligence** defines the language model the agent will use to understand the user and generate responses. This setting directly affects comprehension quality, response speed, and overall consistency.

The language model is the conversational brain of the assistant. It understands user intent, maintains call context, follows the rules defined in the prompt, uses the knowledge base, and generates the appropriate response in each turn.

The models shown in this setup include **Neuron 1.0**, **GPT-OSS 120B**, **GLM-4.5 Air**, **GPT-4.1 Nano**, **GPT-5 Nano**, **Gemini 2.5 Flash Lite**, **Gemini 2.5 Flash**, and **Claude Haiku 4.5**.

For appointment-focused agents and scheduling workflows, **Gemini 2.5** is the practical recommendation.

### Temperature

**Temperature** controls how much variation the agent introduces in its responses. A lower temperature produces more stable, focused, and predictable answers. A higher temperature introduces more variation and less control.

For support, service, appointment, and operational agents, a controlled temperature is usually the right choice.

### Call Direction

**Call Direction** defines how the agent participates in the calling flow. The available modes are **Outbound**, **Inbound**, and **Both**.

**Outbound** is used for outgoing calls such as campaigns, reminders, confirmations, and follow-up. **Inbound** is used for incoming calls such as support, reception, appointments, customer service, or general information. **Both** allows the same agent to work in both scenarios.

### Saving and validation

**Save** stores the current agent configuration. **Clear** removes or reverts the current unsaved edits.

Every major change should be validated through real testing before the configuration is considered finished. This includes checking the opening message, listening to the voice, validating the active languages, confirming the selected model, confirming the call direction, and reviewing dynamic variable values.

> **Important:** A good Agent setup should sound clear in a real call, not only look correct in the editor.

**Workflow** defines the decision structure of the agent. While the **Agent** tab sets the assistant’s overall identity, **Workflow** determines which path the conversation should follow based on the user’s intent and the logic you design.

This section is where you create the visual conversation routes, conditions, transfers, tool stages, and endings that organize how the call moves from one step to the next.

### What you can do in Workflow

**Workflow** lets you build a visual path for the conversation. From a single entry point, you can create branches, send the call to a specialized subagent, transfer it to another agent or to a phone number, use tools, and end the conversation when the route should not continue.

- Start the flow from **Start**.
- Create multiple routes within the same conversation.
- Use specialized subagents.
- Transfer the call to another agent.
- Transfer the call to a phone number.
- Run tools that already exist.
- Close the conversation with an **End** node.
- Control each route with an **LLM condition**.

### How the canvas is organized

The main **Workflow** area is a visual canvas where you place nodes and connect each node to its next step. The flow starts at **Start** and then expands into one or more routes.

In the upper-left corner of the canvas, zoom controls help you move through the workflow when the logic becomes more complex.

### Start

**Start** is the entry point of the workflow. Every conversation begins here. This node does not respond on its own and does not perform direct actions. Its role is to launch the route and send the conversation to the correct next node.

The **Overview** tab explains the role of **Start** in the flow. The **Edges** tab lists every outgoing route created from **Start**, together with each label and destination node.

### Transitions and conditions

Transitions are the connections that link one node to another. In this setup, the available transition type is **LLM Condition**.

Each transition includes a visible label and an **LLM condition** text that defines when that route should apply.

- Use this route when the user needs technical help with the platform.
- Use this route when the user asks to speak with a person.
- Use this route when the issue is fully resolved and the conversation should end.

### Forward and Backward

Operational configuration is done in **Forward**. **Backward** does not provide additional configuration in this version.

### Complete your workflow setup

**Workflow** includes a validation panel called **Complete your workflow setup**. This panel tells you exactly what is missing before the flow can be saved correctly.

This is especially useful in complex workflows because it points to the exact node or edge that still requires attention.

- An **Agent transfer** node is missing its target agent.
- A **Tool** node has no selected tool.
- A transition is missing its condition text.
- A node or branch is still incomplete.

### Subagent

**Subagent** lets you create a specialized conversation stage inside the same workflow. Use it when one part of the flow needs its own behavior, a narrower objective, or a different configuration from the main agent.

- Use it when one stage of the flow needs its own goal.
- Use it when part of the conversation requires a different voice or model.
- Use it when you need node-level control of knowledge or tools.

### Subagent - General settings

Inside the **General** tab, you can configure the **System prompt**, **Override prompt**, **Voice**, **LLM**, **Eagerness**, and **Spelling patience** for that node.

A subagent is useful for specialized support phases, information-gathering stages before a transfer, or routes that need a different speaking style.

### Subagent - Knowledge Base and Tools

The **Knowledge Base** tab includes **Inherit knowledge base**. When enabled, the node inherits the agent’s knowledge base.

The **Tools** tab includes **Inherit custom tools** and **Add Tool**. When inheritance is enabled, the node uses the agent’s custom tools.

Tools are not created in **Workflow**. They are created and configured in the **Tools** section. In **Workflow**, they are only selected or inherited.

### Tool node

The **Tool** node is used to send the conversation to a stage where the agent can use tools that already exist. In the side panel, this appears as **Tool dispatch**.

This node does not create new tools. Its role is to connect the workflow with tools that have already been configured elsewhere.

### Agent transfer

**Agent transfer** sends the conversation to another agent in your account. This is the right option when the interaction needs to move to a different assistant specialized in another task, another language, or another workflow.

You can choose the target agent, define a delay in milliseconds, write a transfer message, and decide whether that first message should be played.

- I am going to transfer you to the right agent for this request.
- I will now connect you with the assistant specialized in this type of question.

### Phone number transfer

**Phone number transfer** sends the call to a phone number. Use this node when the conversation must leave the agent and continue through a specific phone line.

The available destination types are **Phone number** and **Phone dynamic variable**.

**Phone number** is the correct choice for a fixed destination such as reception, a dedicated sales line, or a fixed support line.

**Phone dynamic variable** is the correct choice when the destination depends on the flow context.

### End

**End** is the node that closes the conversation. When the flow reaches this point, the interaction finishes.

- Use **End** when the issue is fully resolved.
- Use **End** when a branch should close without continuing.
- Use **End** when a stage is complete and the route should not advance further.

### Duplicate and delete

Each node includes controls to duplicate or delete it.

**Duplicate** copies an existing node so you can build similar branches more quickly. **Delete** removes the node from the flow. Before deleting a node, review its connected transitions so an active route is not broken.

### Global settings

**Global settings** contains options that affect the workflow as a whole.

**Prevent infinite loops** adds a safety layer that helps avoid routes that could trap the conversation in a repeating loop without progress.

To disable a workflow, disconnect the **Start** node. Without a connected **Start**, the flow no longer has an operational entry point.

### Save and test

**Save** stores the current workflow. **Clear** removes or reverts the current editing state. The unsaved changes warning indicates that there are still edits that have not been saved.

Always test every route separately before publishing.

> **Common mistake:** A workflow can look complete on the canvas and still fail in practice if a node, tool, or condition was never tested with a real conversation.

**Knowledge Base** connects your agent to a knowledge source that has already been prepared inside Callin. This gives the agent access to broader, structured, and reusable reference content so it can answer with more detailed information than what should live inside the main prompt.

Use this section when the information is too long, too detailed, too structured, or too dynamic to maintain directly in the prompt.

### Quick access

- [Open the Knowledge Base manager](https://app.callin.io/knowledge-base)

### When to use Knowledge Base

**Knowledge Base** is the right choice when the content is extensive, changes frequently, already exists as documentation, or should stay separate from the main prompt for easier maintenance.

- Manuals.
- Frequently asked questions.
- Policies.
- Product guides.
- Support articles.
- Internal reference material.

### What this tab does

This tab is used to link an existing knowledge base to a specific agent. It does not create new content from scratch.

The prompt defines how the agent should behave, while **Knowledge Base** defines what additional reference content the agent can use when answering questions.

### Supported content sources

**Knowledge Base** can work with two sources: **Files** and **Web URLs**.

Use **Files** when the knowledge base is built from uploaded documents. Use **Web URLs** when the knowledge base is built from published pages or documentation available by URL.

### What you see when a base is linked

When a knowledge base is already connected to the agent, the tab shows the selected group name, the number of linked documents, and the actions available to manage that connection.

- Selected group name.
- Linked document count.
- **Clear**.
- **Update**.
- **Change**.

### Main actions

**Change** opens the **Select Knowledge Base** panel and lets you choose a different knowledge base for the agent.

**Clear** removes the knowledge base currently connected to the agent.

**Update** refreshes the current connection so the agent works with the latest linked selection.

### Select Knowledge Base panel

When you click **Change**, the **Select Knowledge Base** panel opens. This panel is used to review available sources, choose a group, inspect its documents or URLs, and confirm the final selection.

- **Source** switches between **Files** and **Web URLs**.
- **Groups** lists the available knowledge bases inside the selected source.
- **Refresh** updates the list of groups.
- **Documents / URLs** shows the resources included in the selected group.
- **Linked** means the resource belongs to the selected base and will be available to the agent once the connection is confirmed.
- **Select** confirms the chosen knowledge base.
- **Close** exits the panel without applying a new selection.

### How the selection flow works

The recommended workflow is always the same: first create and organize the knowledge base in the general manager, then return to the agent and connect that prepared source from this tab.

This keeps creation and selection separate. The general manager builds the knowledge base. The agent tab links it to the conversation.

### Best practices

Link only useful and relevant content. Organize groups by purpose. Use clear group names. Review the selected group before saving. Refresh the connection after important changes.

Keep agent behavior in the prompt and reference content in **Knowledge Base**.

### What this tab does not do

The agent’s **Knowledge Base** tab is not used to write the main prompt, configure tools, build workflows, or create a knowledge source from zero. Its job is specific: select an existing knowledge base and link it to the agent.

> **Tip:** Put behavior rules in the prompt and put reusable reference content in the Knowledge Base. That separation makes updates much easier.

The **Tools** tab defines which tools your agent can use during a call.

This section is used for two different things: adding custom tools to the agent and enabling or configuring the system tools that Callin already includes.

Tools extend what the agent can do during a conversation. While the prompt defines how the agent should speak and **Workflow** defines how the call should move forward, tools let the agent execute specific behaviors at the right moment.

### Quick access

- [Open the global Tools section](https://app.callin.io/tools)

### Two types of tools

This section brings together two distinct groups of tools: **Custom tools** and **System Tools**.

### Custom tools

**Custom tools** are tools created by your team for specific use cases. They are not built inside the agent tab.

First, you create them in the platform-wide **Tools** section. Then you return to the agent and attach them from this tab.

- Query an external system.
- Run an automation.
- Send or receive data through a webhook.
- Trigger business-specific logic.
- Connect the agent to another service.

### Main custom tools area

The main area of the **Tools** tab shows the custom tools already attached to the agent.

If the agent does not have any custom tools attached yet, the section shows the corresponding empty state.

### Add Tool

**Add Tool** is used to attach a custom tool to the agent.

When your account already contains tools, this button lets you search for them and select them. When no tools exist yet, the selector offers a direct option to create a **Webhook Tool**.

### System Tools

**System Tools** are built-in Callin tools that are already available inside the agent.

They are designed to handle common call situations without requiring you to build new tools from scratch. These tools can be enabled or disabled individually, and some of them include advanced configuration.

### Smart Hang-up

**Smart Hang-up** lets the agent end a call correctly when it detects that the conversation has already finished.

This tool is designed for natural call endings and helps avoid keeping the call open unnecessarily once the user has clearly finished.

- The user says goodbye.
- The user says that is all.
- The user confirms the issue is resolved.
- The conversation has clearly reached its end.

### Language Switching

**Language Switching** lets the agent manage language changes during the conversation.

This tool is especially important when the agent works in multiple languages and the user may switch languages at the beginning or in the middle of the call.

### Intelligent Listening

**Intelligent Listening** is a system tool designed to improve how the agent listens to and manages the conversation in real time.

This tool is controlled from the activation toggle.

### Transfer to agent

**Transfer to agent** lets the agent hand the conversation over to another agent.

This is useful when a call needs to move to another specialized assistant inside your account.

- From a general agent to a support agent.
- From an initial agent to a sales agent.
- From a multi-purpose agent to a specialist.

### Transfer to number

**Transfer to number** lets the agent transfer the call to a human phone number.

This is one of the most important tools when you need to escalate a conversation out of the agent and hand it over to a person or a specific line.

- Reception.
- Human support.
- Sales.
- A switchboard.
- A specific office or professional.

### Human Transfer Rules

**Human Transfer Rules** is the block where you define the specific rules for transferring the call to human operators.

Each rule includes **Destination Type**, **Phone Number** or a dynamic phone variable, and **Condition**.

**Destination Type** can be a fixed phone number or a phone number provided through a dynamic variable.

**Condition** defines when that specific transfer rule should apply.

### Voicemail Intelligence

**Voicemail Intelligence** detects when the call has reached voicemail and acts accordingly.

This tool is especially important in outbound agents because it lets you decide what should happen when no person answers and a voicemail greeting is detected.

- Leave the voicemail message blank if the call should end immediately when voicemail is detected.
- Write a voicemail message if you want the system to play a message before ending the call.

### Description and Disable interruption

Several system tools include a **Description** field and a **Disable interruption** control.

**Description** explains to the model how and when the tool should be used. **Disable interruption** controls whether the execution of the tool can be interrupted while it is running.

### How to choose the right tools

Do not enable every tool by default. The right selection depends on how your assistant is expected to work.

An inbound support agent may use **Smart Hang-up**, **Language Switching**, and **Intelligent Listening**. An agent that escalates to humans may use **Transfer to number** together with clearly defined transfer rules. An outbound agent may use **Voicemail Intelligence**, **Smart Hang-up**, and **Language Switching**.

### Best practices

Enable only the tools the agent actually needs. Customize system tools when your operation requires it. Use clear descriptions. Define specific conditions in transfer rules.

Use fixed numbers when the destination is always the same and dynamic variables when the destination depends on context. Create custom tools in the global **Tools** section before adding them to the agent. Always review real behavior after saving.

> **Common mistake:** Enabling too many tools at once usually makes behavior harder to predict, test, and maintain.

**Call Action** automates what happens during and after each call so your agent can turn conversations into follow-up, organization, and practical next steps.

Use **Call Action** when your agent needs to do something useful with the call, not just carry the conversation.

The best setup is not the one with the most actions enabled. It is the one that enables only the actions that add real value to your workflow.

### Quick access

- [Set up Google Calendar](https://app.callin.io/actions/google-calendar)
- [Set up Cal.com](https://app.callin.io/actions/cal)

### What Call Action does

**Call Action** brings together the automations your agent can run during the call or immediately after it ends.

This section turns a conversation into practical outcomes: booking a meeting, sending a follow-up email, logging issues, syncing data with other apps, extracting structured information, and defining automatic call retries.

- Book meetings directly into a calendar.
- Send an automatic summary email after the call ends.
- Give the caller a clear way to opt out of future contact.
- Log issues or complaints detected during the conversation.
- Send captured data to other systems through a post-call webhook.
- Extract structured information from the conversation.
- Store extracted data in the contact profile.
- Configure automatic retries when a call is not completed.

### Appointment Scheduling

**Appointment Scheduling** allows the agent to book meetings directly during the conversation.

This is especially useful for sales, support, onboarding, bookings, and any flow where securing an appointment during the call reduces friction and avoids losing momentum.

### Scheduling Provider

Before enabling **Appointment Scheduling**, connect the scheduling provider you want to use. You can work with **Google Calendar** or **Cal.com**.

Once the account is connected, you can select the calendar or booking configuration the agent will use.

**Google Calendar** is the right choice when you want to schedule directly on connected Google calendars. **Cal.com** is the right choice when your booking operation already runs on Cal.com.

The agent time zone should match the calendar time zone to avoid errors when proposing times or confirming availability.

### Post-Call Summary Email

**Post-Call Summary Email** automatically sends an email when the call ends.

This action keeps owners, teams, or shared inboxes informed without requiring manual follow-up.

- Define the recipients who should receive the email.
- Write a clear subject line.
- Write the base message body.
- Choose the email language.
- Decide whether to include call data.
- Decide whether to include extracted fields.

### Smart Opt-Out

**Smart Opt-Out** gives callers a clear and respectful way to decline future contact.

This action is especially useful in lead generation, outreach, or follow-up flows where opt-out requests must be handled properly.

### Issue and Complaint Tracking

**Issue and Complaint Tracking** allows the agent to identify and log issues or complaints detected during the call.

Enable it when you want a conversation to create a case your team can review, manage, or escalate afterward.

### Data Sync (Post-Call Webhook)

**Data Sync** automatically sends captured call data to another system as soon as the conversation ends.

This is the right option when you work with CRMs, automations, operational integrations, or internal systems that need the data without manual intervention.

Enter the webhook URL that should receive the data and validate in advance which system will receive that information and how it will process it.

### Information Capture (Data Extraction)

**Information Capture** turns the conversation into structured data.

You can define what information the system should identify automatically during the call, such as names, dates, preferences, cities, products of interest, or contact reasons.

### Add Entity

**Add Entity** lets you create a new entity to capture a specific piece of information.

Each entity defines what should be extracted and how it should be stored.

- **Data Type** defines the type of value you want to capture.
- **Identifier** is the internal name used to store that entity.
- **Description** explains exactly what the system should extract.
- **Enum Values** lets you restrict the result to a closed list of valid values when you need more consistent output.

### Capture and Store Contact Data

**Capture and Store Contact Data** saves extracted information directly into the contact profile.

Enable this when you want to reuse captured data in future calls or keep richer contact records.

### Persistence and Connection (Call Retry)

**Call Retry** allows you to configure automatic retries when a call is not completed.

This is especially useful for outbound agents, where a call may go unanswered or reach voicemail.

- **Retry Attempts** defines how many times the system should try the call again before stopping.
- **Wait Time Between Tries** defines how many minutes the system should wait before making the next attempt.

### Best practices

Enable only the actions that add real value to the actual call flow. Connect **Google Calendar** or **Cal.com** before using **Appointment Scheduling**. Use clear subjects and messages in summary emails. Define each extraction entity carefully. Store contact data only when it will be useful later. Verify the webhook before enabling **Data Sync**. Set retry frequency in a way that matches your operation. Always align the agent time zone with the calendar time zone.

> **Important:** Automations should reduce manual work, not create extra cleanup later. Keep only the actions that your team will actually use.

**Website widget** lets you publish your agent directly on a web page through an embedded widget.

This section helps you take your agent outside Callin and make it accessible from your website, landing page, support page, client portal, or any other page where you want to offer voice, chat, or both.

**Website widget** combines two types of setup: the technical integration of the widget on your site and the visual and textual customization of the experience.

### What you can do in Website widget

From this section you can copy the widget integration snippet, choose whether the widget appears embedded or as a floating launcher, select the widget theme, define whether interaction happens by voice, chat, or both, adjust the visual size of the dial, enable or disable realtime transcript, show or hide the mute button, customize colors, and edit the visible widget text.

### Embed snippet

**Embed snippet** is the block that lets you integrate the widget into your website.

Here you get the fragment that must be copied and inserted into the HTML of the page where you want the agent to appear. The **Copy** button copies the snippet so you can paste it directly into your site.

### Where to place the snippet

Paste the snippet into the part of the HTML where you want the widget to appear.

When the selected mode is **Inline embed**, place it exactly where you want the widget to render. When the selected mode is **Floating launcher**, place it near the end of the page body so it behaves as a floating entry point.

### Layout & behavior

**Layout & behavior** controls how the widget is embedded and how visitors interact with it.

### Widget mode

**Widget mode** defines how the widget appears on your website. The available options are **Inline embed** and **Floating launcher**.

- **Inline embed** renders the full widget directly inside the page, exactly where you place the snippet.
- **Floating launcher** shows a floating entry point that opens the widget when the visitor clicks it.

### Embed widget theme

**Embed widget theme** controls the overall visual theme of the public widget. The available options are **Match app theme**, **Light**, and **Dark**.

Choose the theme based on the actual design of your site. Readability and brand consistency should always come first.

### Conversation mode

**Conversation mode** defines how visitors can interact with the widget. The available options are **Voice only**, **Chat only**, and **Voice \+ Chat**.

- **Voice only** limits the interaction to voice.
- **Chat only** limits the interaction to text.
- **Voice \+ Chat** allows users to interact through both voice and chat.

### Appearance

**Appearance** controls the visual style of the widget dial and launcher.

### Widget variant and dial size

**Widget variant** defines the base visual size of the widget. The available options are **Tiny**, **Compact**, and **Full**.

**Dial size** lets you define the minimum and maximum size of the dial in pixels.

### Realtime transcript and mute button

**Realtime transcript** controls whether the widget shows live transcript while the conversation is running.

**Show mute button** controls whether the widget displays a button to mute and unmute the microphone during the call.

### Orb colors

**Orb primary color** and **Orb secondary color** define the main colors of the widget.

Use colors that align with your brand and provide enough contrast to maintain readability and a clean visual experience.

### Dial labels

**Dial labels** let you customize the text shown in the center of the dial depending on the interaction state.

- **Center idle**
- **Center connecting**
- **Center listening**
- **Center interrupt**

### Text labels

**Text labels** let you customize several general interface texts.

- **Main label**
- **Start call**
- **Start chat**
- **End call**
- **Chatting status**
- **Input placeholder for a new conversation**

### Chat UI labels

**Chat UI labels** let you customize the texts specific to the chat experience.

- **Voice tab label**
- **Chat tab label**
- **Chat title**
- **Chat subtitle**
- **Chat status idle, connecting, and live**
- **Chat start label**
- **Chat end label**
- **Chat empty state**
- **Chat input placeholder idle and active**
- **Chat send label**

### How to adapt the widget to your use case

For a commercial landing page, **Inline embed**, a clear or app-matched theme, **Voice \+ Chat**, a **Full** variant, and contact-oriented copy can work well.

For website support, **Floating launcher**, **Chat only** or **Voice \+ Chat**, a **Compact** variant, and help-oriented text often work well.

For a voice-first experience, **Inline embed**, **Voice only**, a larger dial, a visible mute button, and simple direct labels can work very well.

### Best practices

Choose the widget mode based on the space available on your site. Adapt the theme to the actual site design. Use a conversation mode that matches expected user behavior. Review dial size on desktop and mobile. Enable realtime transcript if you want stronger accessibility support. Customize colors without hurting readability. Use labels that are clear, short, and consistent with your brand. Always test the widget on a real page before publishing.

> **Tip:** Before publishing, test the widget on the real page where it will live. Size, colors, and labels often feel different outside the editor.

The **Advanced** tab brings together the fine-tuning settings of the agent. This is where you configure how the agent listens, how it interprets conversations, how it manages silence, how it handles call data, and how it optimizes performance in outbound telephony scenarios.

This section becomes especially important when you want to refine the agent’s behavior with more precision.

**Advanced** is divided into four main blocks: **Voice & Understanding**, **Conversation Flow**, **Privacy & Data**, and **Telephony Extras**.

### Voice & Understanding

**Voice & Understanding** lets you adjust how the agent captures audio and how it prioritizes certain terms during a conversation.

This block is especially useful when the agent works with specific words, names, brands, technical terms, numbers, or vocabulary that should be recognized more accurately.

### Speech Capture Quality

**Speech Capture Quality** defines the audio format the agent will use to process speech.

The available options include **PCM 8000 Hz**, **PCM 16000 Hz**, **PCM 22050 Hz**, **PCM 24000 Hz**, **PCM 44100 Hz**, **PCM 48000 Hz**, and **ulaw 8000 Hz**.

**PCM 16000 Hz** appears as the recommended option. **ulaw 8000 Hz** is designed for telephony scenarios.

**PCM 16000 Hz** is the best starting point for most setups.

### Priority Keywords

**Priority Keywords** lets you add terms that the system should prioritize to improve recognition accuracy.

This field helps the agent recognize important words more reliably, such as brands, company names, product names, sector-specific terms, acronyms, codes, uncommon surnames, or internal vocabulary.

### Conversation Flow

**Conversation Flow** controls the conversational rhythm of the agent.

This block is used to adjust how quickly the agent joins the conversation, how long it waits before responding, how it behaves when someone is spelling slowly, and when it should end a call after silence.

### Eagerness

**Eagerness** controls how quickly the agent joins the conversation after the caller stops speaking. The available options are **Patient**, **Normal**, and **Eager**.

**Patient** makes the agent wait longer before responding. **Normal** offers a balance between speed and naturalness. **Eager** makes the agent respond more quickly.

### Spelling patience

**Spelling patience** makes the agent more patient when a caller is slowly spelling names, email addresses, or identification numbers. The available options are **Auto** and **Off**.

**Auto** is the recommended option when the agent needs to collect information that is often spelled out or spoken slowly.

### Take turn after silence

**Take turn after silence** defines how many seconds the agent should wait after the caller stops speaking before taking its turn.

### End conversation after silence

**End conversation after silence** defines the length of silence after which the call ends automatically if the caller stops responding.

### Max conversation duration

**Max conversation duration** defines the maximum allowed length for a single call.

### Privacy & Data

**Privacy & Data** controls how call data is handled and helps you balance operational quality, internal review, privacy, and compliance.

### Record Calls

**Record Calls** allows the system to securely store call transcripts and audio.

Enable this option only if it aligns with your internal privacy, storage, and compliance policies.

### Telephony Extras

**Telephony Extras** groups telephony-specific settings, especially those focused on improving outbound calling performance.

### Number Rotation

**Number Rotation** automatically rotates among the available phone numbers.

This helps reduce the risk of a number being flagged as spam, distribute call volume across multiple numbers, improve deliverability, and make outbound operations more resilient.

### Select Phone Numbers and Calls Per Number

**Select Phone Numbers** lets you choose which numbers will participate in rotation. When **Number Rotation** is enabled, at least one number must be selected.

**Calls Per Number** defines how many calls the system places from one number before switching to the next number in the rotation.

### State-Based Restriction

**State-Based Restriction** limits calls so the agent dials using a local number from the same state as the contact.

This feature is designed for US local numbers and requires compatible local numbering in the account.

### Best practices

Use **PCM 16000 Hz** as the starting point. Add **Priority Keywords** only for truly important terms. Keep **Eagerness** at **Normal** unless the use case clearly requires a different rhythm. Enable **Spelling patience** when the agent collects sensitive or spelled-out data. Review silence settings carefully. Use **Record Calls** only if it fits your internal policies. Enable **Number Rotation** only when you actually have multiple useful numbers available. Confirm that **State-Based Restriction** has real support in your account before enabling it.

> **Important:** Advanced settings are most useful when you change them with a clear reason and test the result with real calls.
